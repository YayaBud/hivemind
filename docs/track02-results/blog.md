# What a local memory graph can prove

A persistent memory system is easy to oversell. A search result can look fluent while omitting the one message that changes the answer. We built a harder local benchmark to measure whether retrieved evidence actually supports a question, then ran it against the same data through a local FalkorDB-backed store.

The benchmark uses a frozen snapshot of 1,595 redacted messages and 445 scoped notes from Claude, Codex, and Antigravity work on one project. It contains 12 development questions and 18 held-out questions. Eight cases require evidence from multiple source records. Four cases target the tail of a specific agent session, where “latest” means the final user-authored record in that session. Other cases test temporal reasoning, state changes, input behavior, procedural notes, uncertainty, and conflicting or incomplete project status.

The authoritative data lives in FalkorDB. Python builds a derived retrieval graph from a consistent snapshot so traversal, token budgets, provenance, and scoring stay reproducible. The store keeps chat messages in agent graphs and shared memories in a common workspace graph. It records message order, handoffs, supersession, procedural memory, source identifiers, and timestamps. A workspace setting isolates graphs on the local server; it is a deployment boundary, not a SaaS multi-user authorization model.

Scoring measures complete evidence retrieval. A case passes only when every required evidence group has an approved source record and every required pattern appears in the returned card text. The score says nothing about whether a newly generated answer would be correct. This round made no fresh model calls and measured no billing or production latency savings.

The strongest held-out result used hybrid retrieval with an 800-token context budget: 10 of 18 cases were complete, covering 21 of 33 evidence groups with 14,068 context tokens. The primary budget comparison is flat at 1,200 tokens: it completed 6 of 18, covered 15 of 33 groups, and used 21,393 context tokens. Hybrid 800 therefore used 34.24% fewer context tokens than flat 1,200 while retrieving more complete evidence groups. At the same 800-token budget, hybrid covered 21 of 33 groups versus flat's 12 of 33, with 14,068 versus 14,059 context tokens; that pair shows coverage improvement without context-token savings.

The development split tells a similar but separate story. On the local FalkorDB backend, hybrid at 800 tokens completed 8 of 12 cases and covered 13 of 19 groups. Flat at 800 completed 6 of 12 and covered 9 of 19. The older offline engine run reached 9 of 12 and 14 of 19, so those numbers are not interchangeable with the database-backed result. Canonical source metadata and snapshot normalization changed card packing. We preserve both runs instead of selecting the more flattering one.

The design also exposes failure modes. A latest request can rank below ordinary project notes because its wording is short. A multi-source question can retrieve one strong record while dropping a second record at the token boundary. A status question can surface a plan paragraph without its later pending update. These are retrieval failures, not reasons to silently relax the grader. The next useful experiments are question rewriting and embeddings, treated as hypotheses to evaluate against a newly sealed holdout. The current holdout remains a regression check and must not be reused for tuning.

The practical architecture is deliberately modest: FalkorDB is the persistent authority, while the Python context graph is a bounded derived cache. MCP tools expose compact source, author, status, and time metadata. Handoffs and supersession remain explicit graph relationships. This gives a durable local memory substrate with inspectable evidence and honest limits, rather than a claim that every recalled answer is true.

The operational discipline matters as much as the graph model. Every benchmark run records the source hash for the retrieval engine, the fixture hash, the frozen corpus hashes, the backend, the workspace, and the context revision. The runner compares the local snapshot by original source ID and redacted text before it builds the derived index. It refuses a run when a source changes, when the snapshot is inconsistent, or when another writer changes the workspace revision during measurement. That makes a result auditable without exposing raw transcripts or credentials.

The benchmark also keeps development and held-out questions separate. Development results can guide engineering decisions; held-out results remain a final check against overfitting. The public report therefore shows misses and latest-request failures alongside successes. A memory system earns trust by making its evidence boundaries visible: a missing source is a missing source, a pending plan remains pending, and a retrieved assistant report does not become independent verification merely because a graph returned it.
